# Large retained archives

The history dashboard uses `GET /api/history/cursor` with the existing filters, optional opaque `cursor`, and `page_size` (1–200). It retrieves a bounded page in descending UTC microsecond timestamp/event-ID order. SQL aggregates calculate matching request totals using the same inclusive-cache/reasoning semantics as detailed analytics. Unpriced costs remain unavailable. Lifecycle events appear in the event list but are excluded from request totals.

The first page establishes an arrival watermark. Subsequent pages exclude new arrivals, including backdated telemetry, so ingestion does not shift offset pages. Refresh starts a new window. A persistent monotonic arrival sequence also survives deletions and SQLite ROWID reuse. Corrections and deletions to existing records may remove them from that window: this is not a retained historical database snapshot. Filter changes require a fresh cursor. Cursors contain no credentials and cannot select another account; every query resolves the store from the authenticated account. Previous-page navigation retains cursor positions locally.

Indexes support timestamp order and exact provider/model/tool/project/device/request filters. Initial index/sequence setup can take time on an existing large ledger and uses the store lock. Subsequent page responses avoid constructing full event or optimization-report lists. SQL aggregation still scans matching records; this is bounded Python memory, not constant database work. Free-text exact filter inputs avoid transferring an unbounded list of historical session identifiers.

Detailed optimization analysis is an explicit **Run detailed filtered analysis** action using `/api/history/analysis`. It retains the existing full-history evidence analysis and can use substantial memory on large archives. It examines the current ledger, which may differ from a cursor browsing window. Individual request investigation remains available.

`GET /api/history/export` streams the complete filtered JSON ledger using a separate read-only SQLite connection, one consistent read transaction, and batches of 256 rows. It never builds the full export in Python memory. Long downloads can retain WAL pages until their read snapshot closes; operators should monitor disk space. The browser downloads a Blob without parsing/re-serializing the JSON, but still holds the download bytes. For very large exports use an authenticated HTTP client and stream directly to disk. Export uses current retained history, independently of browsing cursors. Existing `/api/export` and offset `/api/history` remain compatibility endpoints; clients should migrate to the new routes for bounded retrieval.

Validation includes SQL/reference accounting parity, 1,051-event tied timestamp traversal, concurrent backdated arrivals, deletion/ROWID reuse, malformed cursors, authenticated tenant isolation, date filtering, and consistent streamed snapshots without full-ledger helpers. Frontend tests cover cursor/filter encoding and UTC end-day semantics. No distributed-load or browser memory SLA is claimed.
